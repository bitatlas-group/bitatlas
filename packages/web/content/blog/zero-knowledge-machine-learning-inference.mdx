Most machine learning deployments force an uncomfortable trade: to get a prediction, you hand your raw data to whoever runs the model—or, if you run the model yourself, you trust that the operator computed honestly. Zero-knowledge machine learning (zkML) and homomorphic encryption (FHE) break that trade. They let one party prove a model produced a specific output, or compute on data it never sees in the clear, without revealing the inputs, the weights, or both.

For anyone building privacy-first infrastructure, these are the primitives that turn "trust us" into "verify it." This post covers how they work, where each one fits, and what they actually cost in production.

## Two Different Problems

"Private inference" is really two separate guarantees, and conflating them is the most common mistake engineers make when they start:

- **Integrity**: prove that `output = model(input)` was computed correctly, without re-running it. This is what zero-knowledge proofs give you.
- **Confidentiality**: compute `model(input)` without the compute party ever seeing `input` (or the data owner seeing the weights). This is what homomorphic encryption gives you.

You sometimes want one, sometimes the other, occasionally both. Picking the wrong primitive for your threat model means paying enormous cost for a property you did not need.

## Zero-Knowledge Proofs for Inference (zkML)

With zkML, the party running the model generates a succinct cryptographic proof that it executed a specific computation on some input and got a specific result. A verifier checks the proof in milliseconds without learning the input and without redoing the work.

The mechanics: you express the forward pass of the network as an arithmetic circuit, then prove satisfiability of that circuit with a zk-SNARK or zk-STARK. Every multiply-accumulate, every activation, becomes a set of constraints the prover must satisfy.

Where this shines:

- **Verifiable off-chain compute**: an oracle or rollup proves it ran the agreed model, so a smart contract can trust the result without trusting the operator.
- **Auditable agent decisions**: an AI agent proves a flagged transaction really came from the published fraud model, not a quietly swapped one.
- **Selective disclosure**: prove "this medical image was scored above the threshold by model v3" without revealing the image.

The hard part is cost. Proving is expensive and grows with model size. A small model proves in seconds; a transformer with hundreds of millions of parameters can take minutes to hours and a lot of memory. The standard mitigations are quantizing weights to small integers, proving only the decision-relevant layers, and batching many inferences into one proof. Verification, by contrast, stays cheap—often under a few milliseconds regardless of model size, which is exactly why the asymmetry is useful.

## Homomorphic Encryption for Inference (FHE)

Fully homomorphic encryption lets you run computations directly on ciphertext. The data owner encrypts the input, the server runs the model on the encrypted values, and the encrypted result comes back—decryptable only by the owner. The server learns nothing about the input or the output.

```python
# Conceptual shape of an FHE inference call
ctx = fhe.context(scheme="CKKS")
enc_input = ctx.encrypt(features)        # client side
enc_output = model.forward(enc_input)    # server runs on ciphertext only
prediction = ctx.decrypt(enc_output)     # client side
```

The CKKS scheme is the workhorse for ML because it supports approximate arithmetic on real numbers, which is what neural networks need. The catches are concrete:

- **Nonlinearities are painful.** ReLU, softmax, and argmax are not natively homomorphic. You approximate them with low-degree polynomials, which changes accuracy and constrains architecture.
- **Multiplicative depth is budgeted.** Each multiplication adds noise. Go past your budget and you must bootstrap—a costly refresh step—or the result decrypts to garbage.
- **It is slow.** Encrypted inference can run three to six orders of magnitude slower than plaintext. A model that scores in under a millisecond in the clear may take seconds per encrypted query.

FHE fits best when confidentiality is non-negotiable and latency is forgiving: a clinician scoring an encrypted genomic profile against a proprietary model where neither side may see the other's asset, or a bank scoring encrypted customer features on a third-party risk model.

## Choosing Between Them

A quick decision guide:

- Need to prove a result was computed honestly, and the input can be revealed to its owner but not the verifier? Reach for **zkML**.
- Need the compute party to never see the input at all? Reach for **FHE**.
- Need both verifiability and confidentiality? Compose them—run FHE inference, then prove correctness of the encrypted computation—and budget accordingly, because you pay both bills.

For most application developers the honest answer in 2026 is that full-network private inference is still reserved for high-value, low-throughput cases. The pragmatic middle ground is to keep the heavy model on infrastructure you control with strong encryption at rest and in transit, and apply zkML or FHE only to the narrow, sensitive step that truly needs it.
